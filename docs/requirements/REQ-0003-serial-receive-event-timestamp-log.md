## 1. 目标

派蒙助手需要把串口接收到的连续原始字节处理成完整接收事件，形成“接收 -> 严格分帧 -> 打包事件 -> 显示与日志保存”的完整链路。

本需求增加的是接收层的数据帧边界识别和事件结构化，不解析载荷内部的业务字段，不改变既有发送端的原始字节行为。

## 2. 范围

### 2.1 包含范围

1. 按 `\r\n` 识别接收数据帧。
2. 为每个完整数据帧生成一个 `ReceivedEvent`。
3. 在读到完整帧结束符后记录时间戳。
4. 在接收区按文本或 HEX 模式显示事件。
5. 无论时间戳显示开关状态如何，都将完整接收事件写入按日期划分的日志。
6. 提供时间戳显示开关、日志保留清理和日志目录入口。
7. 将日志故障与串口接收、事件队列和界面显示隔离。

### 2.2 不包含范围

1. 不解析载荷内部的业务字段。
2. 不增加帧头、长度字段、命令字、校验和、JSON、Modbus 等业务协议字段。
3. 不把时间戳写入发送给设备的串口字节。
4. 不自动在发送数据末尾追加 `\r\n`。
5. 不把发送数据写入本需求的接收日志。

## 3. 术语

本需求使用的领域术语见项目上下文文档 [`CONTEXT.md`](../../CONTEXT.md)。核心定义如下：

- **数据流**：从串口连续到达的原始字节序列。
- **数据帧**：以 `\r\n` 作为结束边界的一条完整数据。
- **载荷**：数据帧中不包含末尾 `\r\n` 的原始字节内容。
- **原始帧**：包含末尾 `\r\n` 的完整数据帧字节内容。
- **接收事件**：一条数据帧完成后形成的、携带该帧接收时间和数据内容的记录。
- **解析**：从连续数据流中识别数据帧边界并生成接收事件，不解释载荷内部业务字段。

## 4. 接收数据协议

### 4.1 分帧规则

1. 只有连续出现的两个字节 `0D 0A`，即 `\r\n`，才是数据帧结束边界。
2. 单独的 `\r` 不结束数据帧，必须等待后续字节。
3. 单独的 `\n` 不结束数据帧，作为载荷字节保留。
4. `\r\r\n` 中，前一个 `\r` 属于载荷，最后两个字节 `\r\n` 才是结束边界。
5. 不对其他换行形式做自动转换或规范化。
6. 任意出现的连续 `0D 0A` 都是结束边界；本协议不定义载荷内 `\r\n` 的转义机制。
7. 原始数据必须按实际收到的字节保留，不因显示模式、编码或日志格式改变。

### 4.2 跨读取块与多帧

1. `\r` 和 `\n` 可能分属不同的串口读取块，解析器必须正确拼接识别。
2. 一次读取包含多条完整数据帧时，必须按顺序拆成多个独立事件。
3. 未遇到 `\r\n` 的尾部字节暂存在解析缓冲区中，不生成事件、不记录时间、不显示、不写日志。
4. 连接关闭、读写异常导致连接失效或用户点击“清空”时，必须丢弃未完成尾部，不能与其他连接或清空后的数据拼接。
5. 空数据帧 `\r\n` 是合法事件，其载荷为空，原始帧为 `0D 0A`。

### 4.3 超长数据帧

1. 未遇到 `\r\n` 前，单个未完成帧的载荷长度不得超过 `1 MiB`；恰好 `1 MiB` 的载荷仍然有效，收到其后的第一个载荷字节时才判定超长。
2. 超过 `1 MiB` 时，当前帧判定为无效。
3. 解析器丢弃当前已缓存内容，并持续丢弃后续字节，直到识别到下一个 `\r\n`。
4. 超长帧不生成接收事件、不记录时间戳、不写入接收日志。
5. 找到下一个 `\r\n` 后恢复正常分帧。
6. 同一段连续溢出只产生一次诊断提示，不能因异常输入刷屏。
7. 连接关闭或点击“清空”时清除溢出状态。

## 5. 接收事件协议

每个完整数据帧必须打包为一个 `ReceivedEvent`，内部协议固定为：

```text
ReceivedEvent {
    received_at_ms: int
    payload: bytes
    raw_frame: bytes
}
```

字段约定：

1. `received_at_ms` 是 Unix epoch 毫秒整数。
2. 时间戳在程序读到该事件完整的 `\r\n` 后记录，表示程序识别到该事件结束边界的时间。
3. `payload` 不包含末尾 `\r\n`。
4. `raw_frame` 包含完整原始帧，包括末尾 `\r\n`。
5. 事件不保存依赖当前界面设置的文本或 HEX 字段；显示内容在界面渲染时生成。
6. 一次读取中的多个事件分别记录时间戳。它们的时间戳允许相同，也允许因毫秒时钟推进而不同。
7. 日志文件日期按事件完整结束时的本地日期决定；跨午夜完成的事件写入次日文件。

### 5.1 实现接口与队列契约

1. `ReceivedEvent` 是不可变记录；实现使用等价于 `dataclass(frozen=True)` 的数据结构。`payload` 和 `raw_frame` 在构造时复制为稳定的 `bytes` 快照。
2. 无 Qt 的 `ReceiveFramer` 公开接口固定为：

   ```text
   ReceiveFramer(clock_ms, max_payload_bytes=1_048_576, on_overflow=None)
   feed(data: bytes) -> list[ReceivedEvent]
   reset() -> None
   ```

3. `feed()` 按输入顺序返回本次识别出的完整事件；没有完整帧时返回空列表。`reset()` 丢弃未完成尾部和超长帧丢弃状态，不生成事件。
4. `clock_ms` 是无参数可调用的毫秒时间源。每个事件只在识别到其结束边界 `0D 0A` 的处理点调用一次，并将返回值写入 `received_at_ms`。
5. `on_overflow` 只在一次连续溢出开始时调用一次；回调不得直接操作 Qt。串口会话将该诊断转入线程安全的 `diagnostic_queue`，主线程再更新界面提示。
6. 当前会话的 `received_queue` 只允许放入 `ReceivedEvent`，不再放入裸 `bytes`；`error_queue` 继续传递运行时错误文本，`diagnostic_queue` 传递分帧诊断。REQ-0001 中针对裸字节接收队列的旧测试属于历史契约，实施 REQ-0003 时应迁移为事件契约，不增加双轨兼容路径。

## 6. 接收区显示

### 6.1 显示开关

1. 增加“显示时间戳”开关，控件类型为 `QCheckBox`，对象名为 `timestamp_checkbox`。
2. 开关只控制界面是否显示时间戳，不控制串口接收、事件生成、事件队列或日志保存。
3. 每次启动软件时默认开启时间戳显示，不记住用户上次的开关状态。
4. 切换开关时重新渲染全部内存中的完整接收事件。
5. 未完成帧和超长帧不显示。
6. 主界面增加“日志目录”按钮（`QPushButton`，对象名 `log_dir_button`）和日志错误红色标签（`QLabel`，对象名 `log_error_label`）；日志失败提示持续显示到本次运行结束或后续明确状态替换，不使用模态弹窗。
7. 主界面增加接收诊断红色标签（`QLabel`，对象名 `receive_error_label`）显示超长帧的一次性诊断；固定提示文本为“接收帧超过 1 MiB，已丢弃”；不弹 `QMessageBox`，不影响正常接收显示。

### 6.2 时间格式

界面时间戳使用本地时间，格式为：

```text
HH:mm:ss.SSS
```

开启时间戳时，事件显示前缀为时间格式包在方括号中并后跟一个空格，例如 `[09:12:03.125] `。

关闭时间戳时，只去除前缀，事件数据内容保持不变。

### 6.3 文本模式

1. 文本模式显示事件的 `payload`，不显示 `raw_frame` 中的 `\r\n` 字节。
2. 使用当前选择的 UTF-8 或 GBK 编码解码 `payload`。
3. 每个接收事件完成后在显示区形成一个事件分隔换行。
4. `payload` 内实际存在的其他控制字节按当前文本解码结果显示。
5. 时间戳开关、接收模式切换或编码切换不能改变内存中的事件和原始字节。

示例：

```text
[09:12:03.125] Hello
[09:12:04.006] World
```

### 6.4 HEX 模式

1. HEX 模式显示完整的 `raw_frame`。
2. 每个字节显示为大写、两位十六进制，并以空格分隔。
3. `raw_frame` 的结束符显示为 `0D 0A`。

示例：

```text
[09:12:03.125] 48 65 6C 6C 6F 0D 0A
```

## 7. 接收日志

### 7.1 文件位置与命名

1. 日志目录为当前 Windows 用户的本地应用数据目录：

   ```text
   %LOCALAPPDATA%\PaimonAssistant\logs\
   ```

2. 日志目录不存在时，在首次写日志或用户打开日志目录入口时自动创建。
3. 日志文件按事件完整结束时的本地日期命名：

   ```text
   YYYY-MM-DD.txt
   ```

4. 每个日期使用一个 TXT 文件。
5. 文件内容使用 UTF-8 编码。
6. 日期只出现在文件名中，每条日志记录不重复写年月日。

### 7.2 记录格式

1. 只有完整的 `RX` 接收事件写入日志。
2. 每个事件占一行，按接收事件形成顺序写入。
3. 日志时间使用事件的本地时间，格式为 `HH:mm:ss.SSS`。
4. 日志固定记录完整 `raw_frame` 的 HEX，不受界面文本/HEX模式或编码选择影响。
5. HEX 使用大写、两位一组、空格分隔。
6. 日志记录格式为：

   ```text
   [HH:mm:ss.SSS] RX <RAW_FRAME_HEX>
   ```

7. 示例：

   ```text
   [09:12:03.125] RX 48 65 6C 6C 6F 0D 0A
   ```

8. 空帧记录为：

   ```text
   [09:12:03.125] RX 0D 0A
   ```

9. 时间戳显示开关关闭时，日志仍然保存时间戳。
10. 用户发送的数据不写入本需求的接收日志。

### 7.3 写入时机与故障隔离

1. 每个完整事件形成后立即进入日志写入流程，并在正常写入成功后及时刷新文件。
2. 日志写入不得阻塞 reader、停止分帧、丢弃事件或关闭串口接收链路；由于已确认由主线程同步写入，不承诺 Qt 主线程在磁盘 I/O 期间绝对无暂停。
3. 日志目录创建失败、日志文件无法打开或写入失败时，立即停止当前运行期间的日志写入。
4. 日志写入失败后不做内存缓冲、不做重试、不设待重试队列，也不设置 `64 MiB` 等待写队列上限。
5. 日志错误通过 Python 标准库 `logging` 写入应用系统日志；实现使用模块级 logger（例如 `logging.getLogger(__name__)`）记录原始异常及上下文；本需求不要求 Windows Event Log，除非外部交付流程另行指定。
6. 界面显示明确的红色提示：

   ```text
   日志写入失败，请检查磁盘空间或权限
   ```

7. 日志故障不得影响：
   - 串口继续接收数据；
   - 接收事件继续生成；
   - 事件队列继续工作；
   - 接收区继续显示数据；
   - 用户继续进行其他串口操作。
8. 日志只是辅助记录，不能成为串口核心功能的单点故障。

### 7.4 日志服务接口与失败状态

1. 无 Qt 的日志服务至少提供 `ensure_directory() -> None` 和 `write_event(event: ReceivedEvent) -> bool`；日志目录、日期转换函数和文件操作均可注入测试替身。`ensure_directory()` 失败时向调用方抛出明确的 `ReceiveLogError`。
2. `write_event()` 成功写入并刷新后返回 `True`。首次目录创建、文件打开、写入或刷新失败时，服务立即标记为本次运行已熔断，记录原始异常并向调用方抛出 `ReceiveLogError`。
3. 熔断后的后续 `write_event()` 不访问文件系统、不缓存事件、不重试，直接返回 `False`；主窗口只处理首次错误提示。
4. 日志目录入口只调用 `ensure_directory()`，再由主窗口注入的 Windows 目录打开器打开目录本身；日志服务不负责 Qt 或进程启动。

## 8. 日志保留清理

1. 程序启动时执行一次日志清理。若日志目录尚不存在，视为无文件可清理并跳过，不因目录不存在报错，也不为启动清理单独创建目录；首次写日志或用户打开日志目录入口时再创建目录。
2. 程序持续运行跨过本地日期后，在新日期首次写日志前再次执行清理。
3. 只处理日志目录中名称严格匹配 `YYYY-MM-DD.txt` 的普通文件。
4. 按文件名日期和当前本地日期判断保留期限，不按文件修改时间判断。
5. 保留当天及此前 30 个日历日的日志。
6. 删除日期早于当前日期前 30 天的日志文件。
7. 文件名不符合日期格式的文件、子目录和其他文件不得删除。
8. 删除单个日志文件失败时，不影响串口接收和显示；该文件留待下一次清理。
9. 清空接收区不得删除任何日志文件。

## 9. 日志目录入口

1. 主界面提供“日志目录”入口。
2. 点击入口后自动创建日志目录（如果目录不存在）。
3. 使用 Windows 文件资源管理器打开日志目录，而不是只打开某个日期日志文件。
4. 打开目录或创建目录失败时，主窗口在 `log_error_label` 显示包含失败原因的明确错误（例如 `日志目录打开失败：<异常信息>`），但不得影响串口接收、事件生成或接收显示。

## 10. 清空行为

点击“清空”时同时执行：

1. 清除当前接收显示内容。
2. 清除内存中的完整接收事件和时间戳历史。
3. 清空解析器中尚未完成的尾部字节。
4. 清除超长帧丢弃状态。
5. 丢弃点击时事件队列中尚未显示的旧接收事件。
6. 点击后新到达的数据正常进入新的接收链路。
7. 不删除、不修改已经写入的日志文件。

### 10.1 清空的并发线性化点

1. 主窗口清空时调用当前控制器会话的 `reset_receive_session()`；该操作在会话锁内完成，作为“清空前数据”和“清空后数据”的唯一线性化点。
2. `reset_receive_session()` 递增会话代次，重置当前分帧器，替换接收事件队列和诊断队列，并丢弃旧队列对象中的待处理项目。reader 只在同一会话锁保护下完成分帧结果发布，并在发布前确认代次仍有效。
3. 清空完成后到达的数据使用新代次、新分帧器和新队列；清空前尚未显示的事件、未完成尾部和溢出状态均不得进入新历史。连接关闭、读写异常和重新打开也遵循同一会话隔离规则。
4. 控制器未打开时，清空只清理主窗口历史和本地显示状态，不创建串口连接。

## 11. 发送行为

1. 发送区继续支持文本和 HEX 两种模式。
2. 文本模式按当前编码发送原始字节。
3. HEX 模式发送用户输入解析出的原始字节。
4. 发送端不自动追加 `\r\n`。
5. 发送区沿用现有单行 `QLineEdit` 输入；文本模式不自动追加结束符。需要发送 `\r\n` 时，切换到 HEX 模式显式输入 `0D 0A`。
6. 发送数据不生成 `ReceivedEvent`，不进入接收解析链路，也不写入本需求的 `RX` 日志。

1. REQ-0001 作为历史需求记录保留，不修改其原始正文。
2. 本需求新增并覆盖 REQ-0001 中“接收端只传递裸字节、只展示原始数据”的接收层范围。
3. 本需求仍保留 REQ-0001 关于“不解析载荷内部业务协议”的边界。

5. 后续用户说明和功能描述应以本需求为准，不能继续把本需求描述为“不解析接收协议”。

## 13. 验收标准

1. `A\r` 与后续 `\n` 分属两个读取块时，能生成一个完整事件。
2. 一次读取得到 `A\r\nB\r\n` 时，能按顺序生成两个事件。
3. 单独 `\r`、单独 `\n` 和 `\r\r\n` 的处理符合严格 `0D 0A` 规则。
4. `\r\n` 能生成空载荷事件。
5. 未完成尾部在关闭连接或点击清空后不会与新数据拼接。
6. 超过 `1 MiB` 且没有结束符的数据不会生成事件或日志，并能在下一个 `\r\n` 后恢复解析。
7. 每个事件包含正确的 `received_at_ms`、`payload` 和 `raw_frame`。
8. 时间戳在完整 `\r\n` 被识别后记录，多帧事件按顺序独立记录。
9. 文本模式、HEX 模式和 UTF-8/GBK 切换能正确重绘事件历史。
10. 时间戳显示开关默认开启，关闭只改变显示，不改变事件和日志。
11. 日志按本地日期写入正确的 `YYYY-MM-DD.txt` 文件，事件时间不重复写日期。
12. 日志记录保存完整原始帧 HEX，并包含 `0D 0A`。
13. 日志写入失败时显示指定红色提示、写入系统日志，并且接收、事件队列和显示继续工作。
14. 日志失败后不产生内存缓冲或重试队列。
15. 启动及跨日首次写日志前能清理超过 30 天的日期日志，且不误删其他文件。
16. “日志目录”入口能打开日志目录。
17. 点击清空不会删除日志，且清空前的尾部和待显示旧事件不会泄漏到清空后；清空边界由会话代次和会话锁线性化。
18. 发送数据不自动追加 `\r\n`，不进入 `RX` 日志。

## 14. 技术与交付约束

1. 运行平台：Windows 10 / 11。
2. Python：3.10 / 3.11。
3. GUI：PySide6 6.6+。
4. 串口通信：pyserial 3.5+。
5. 测试使用 fake serial、fake 时间源和 Qt offscreen 环境，不依赖真实串口或显示器。
6. 后续实现应补充针对分帧、事件协议、时间戳、日志轮转、日志故障隔离和清空行为的自动化测试。
7. 当前开发环境的 com0com 端口为 `COM17 <-> COM19`，默认手工串口验收使用该端口对和 `115200 / 8 / N / 1` 流程。端口号由 Windows/com0com 分配；文档中的 `COM3 <-> COM4` 仅为下载 com0com 前的示例，不是固定要求。真实设备不是自动化测试前置条件。
8. 若使用真实设备验收，必须另外确认端口、波特率、数据位、校验位、停止位、编码以及断开/恢复测试方法。

## 15. 已确认的实施决策

1. 在串口读取会话边界完成分帧：每次打开连接创建独立的分帧器和接收事件队列，reader 线程将完整 `ReceivedEvent` 放入该会话队列；主窗口只消费事件，不负责从裸字节重新判断帧边界。
2. 分帧器使用可注入的毫秒时间源，在识别到完整 `\r\n` 的同一处理点记录 `received_at_ms`；因此时间戳表示程序识别事件结束边界的时间，而不是界面定时器取出事件的时间。
3. 日志写入由主线程消费事件时同步执行单行写入并及时刷新。reader 线程不执行文件 I/O，日志故障不会阻塞串口读取；日志首次失败后立即熔断本次运行期间的后续写入，不建立失败缓存、不重试。
4. 日志服务、分帧器和事件渲染器均保持无 Qt 依赖，并通过时间源、日志目录和文件操作等依赖注入实现可重复测试；Qt 主窗口只负责协调控件、队列和错误提示。
5. 清空操作在主线程中同时清除显示、事件历史、当前会话分帧状态和待消费的旧事件；清空不会删除已写入的日志文件。
6. 日志写入虽然由主线程同步执行，但保证范围是“不阻塞 reader、不停止分帧、不丢弃事件生成”；不承诺 Qt 主线程在磁盘 I/O 期间始终无阻塞。若需要 UI 线程也绝不因磁盘 I/O 暂停，必须另行改定为独立日志线程架构。
7. 发送区保留现有单行输入和回车发送行为；发送端不自动追加 `\r\n`，文本模式不提供直接输入换行的多行编辑能力，需要发送结束符时使用 HEX 模式显式输入 `0D 0A`。

## 16. 测试决策

1. 测试以外部可观察行为为准，优先验证事件内容、顺序、显示结果、日志文件内容、错误提示和串口操作是否继续可用，不依赖线程内部实现细节。
2. 分帧器测试使用 fake 时间源，覆盖严格 `0D 0A` 边界、单独 `\r`/`\n`、跨读取块、多帧、空帧、`\r\r\n`、未完成尾部清理、超长帧恢复和每个事件的时间戳。
3. 事件渲染测试覆盖文本与 HEX 模式、UTF-8/GBK、时间戳开关、历史重绘、事件分隔换行和原始字节不可变性。
4. 日志服务测试注入临时目录、fake 本地时间和可控文件操作，覆盖日期文件命名、格式、刷新、跨日切换、30 日保留清理、非目标文件保护、删除失败和写入失败熔断。
5. 主窗口测试沿用现有 Qt offscreen 与 fake controller 模式，覆盖事件队列消费、日志失败后的接收显示隔离、清空前尾部与旧事件丢弃、日志目录入口和发送行为回归。
6. 串口控制器测试验证每个连接使用独立会话队列，关闭或异常后未完成数据不会泄漏到新连接；真实串口端到端测试仍作为 Windows 手工验收，不纳入自动化测试依赖。

## 17. 交付门禁与并发边界

1. 当前仓库是 Python/PySide6 项目，仓库内没有 CI workflow、Sonar 配置、Keil `uvprojx` 工程或中文 Doxygen 检查配置；`Sonar new_violations=0`、Keil 双构建同步和中文 Doxygen 不作为本仓库当前 REQ-0003 的验收门禁。
2. 若外部发布流程强制要求上述门禁，必须在实施前提供对应配置、执行入口和判定规则；在此之前不将其假设为本项目的隐藏输入。
3. 多个派蒙助手进程可以追加写入同一日期日志文件。默认只保证单进程内的事件顺序、单行写入和及时刷新，不增加跨进程锁，也不承诺多个进程之间的全局时间顺序或绝对不交错；若需要该保证，应另立数据契约。
4. 自动化门禁应在按 `requirements.txt` 和 `requirements-dev.txt` 安装的干净环境中执行；已有本地环境与依赖声明不一致时，不以该环境的通过结果替代可复现门禁。
5. 功能实现完成后，必须更新 `README.md`、`docs/user-manual.md` 和 `CHANGELOG.md` 中受影响的功能、操作说明和版本记录；功能尚未实现前，不把这些能力写成已支持，REQ-0001 原始正文也不因本需求修改。
