## 必须遵守的发布原则

1. **Branches 只保留 `main`，版本保存在 Tags。** 开发期间可使用临时分支/worktree，但不能停在“已推功能分支”的状态；交付必须进入 `main`，新建注释标签 `vX.Y.Z`，交付时 `main` 与该标签指向同一发布提交。确认远端交付成功后再清理已完成的临时分支。
2. 保留历史提交和所有已发布版本标签，不删除、重建或改指向旧标签。同名标签若已指向本次发布提交，核验后幂等继续；若指向不同提交，停止并报告，默认使用新的补丁版本，不强行移动标签。
3. 禁止使用强制推送、历史改写、`git reset --hard`、破坏性 checkout 或无范围的 `git clean`。遇到远端分叉、冲突、权限不足或不能证明安全的独有改动时，停止相关操作，不覆盖。
4. 本项目是公开开源仓库，不擅自改变可见性。除已跟踪的 `.pi/prompts/update-paimon.md` 外，不提交 `.pi/` 中的其他内容；不提交 `.venv/`、缓存、`build/`、`dist/`、日志、备份、凭据或本机文件。
5. **每个版本都必须把已验证 EXE 纳入根目录 `PaimonAssistant.exe`。** 代码、文档、EXE 在发布提交中一并交付，`main` 和版本标签都必须包含它。README 同时提供 `main` 最新版和版本标签固定下载链接，并公布文件大小与 SHA256；不能只提供源码压缩包。
6. 测试、构建或冒烟验证失败时，不创建发布标签、不推送发布内容。先修复本次改动直接引起的问题；无法完成时保留现场并报告，不声称验证通过。
7. 删除临时分支前证明提交已被 `main` 包含，或补丁等价且原提交已归档。worktree 的未提交改动、未跟踪文件必须检查；独有或不明确的工作先备份并升级处理，绝不为了只剩 `main` 而丢数据。清理目录联接时不得递归删到共用环境。

## 执行流程

### 1. 发布前检查

- 确认当前目录是派蒙助手仓库，读取项目规则、README、需求文档和相关源码。
- 检查 `git status --short --branch`、全部本地/远端分支、worktree、远端地址、最近提交和全部版本标签；最终目标分支固定为 `main`。
- 执行 `git fetch origin --prune --tags`，确认本地与远端基线；不要自动丢弃或覆盖现有未提交改动。
- 区分本次需求相关改动和用户已有的无关改动，只处理并提交本次范围。
- 检查当前版本来源，包括 `paimon_assistant/__init__.py`、README、CHANGELOG 和最新可达的 SemVer 标签。

### 2. 自动确定新版本号

遵循 SemVer，并选择尚未使用的新标签：

- `PATCH`，如 `v0.1.0 -> v0.1.1`：修复错误、安全问题、兼容性优化或仅文档/维护更新。
- `MINOR`，如 `v0.1.0 -> v0.2.0`：增加向后兼容的新功能。
- `MAJOR`，如 `v0.2.0 -> v1.0.0`：存在明确的不兼容变更。

根据实际改动自动判断。若是否属于破坏性变更会影响用户数据、配置或既有使用方式，先向用户确认，不要自行发布重大版本。

### 3. 实现更新

- 先阅读相关实现和测试，明确行为与验收条件。
- 按现有项目结构完成最小且完整的实现，不进行无关重构。
- 为新增行为或修复补充针对性测试；缺陷修复应尽量先建立可复现测试。
- 更新必要的用户说明和需求文档，不虚构尚未实现或尚未验证的功能。

### 4. 更新发布资料

- 将 `paimon_assistant/__init__.py` 中的 `__version__` 更新为新版本。
- 更新 README 中的当前版本和受影响说明。
- 在 CHANGELOG 顶部新增本次版本，写明真实日期、功能或修复、验证结果和仍存在的限制；保留所有旧版本记录。
- 确认代码版本、README、CHANGELOG、发布提交和标签一致；更新旧功能分支下载链接，防止清理分支后链接失效。
- 用既有 handoff 记录当前 `main`、验收结果及备份位置，不新增重复总结文档。

### 5. 完整验证

根据当前环境执行项目可用的全部验证，至少包括：

- Qt offscreen 完整自动化测试。
- 源码 `--smoke-test`。
- PyInstaller 干净打包。
- 打包后的 EXE `--smoke-test`。
- `git diff --check`。
- 敏感信息扫描和待提交文件清单检查。

没有真实串口或 com0com 时，不得声称真实串口验收通过；只报告自动化验证结果和未执行项。

若本次只是把已验收交付同步到 `main`、创建标签或更新发布文档，可复用有明确来源和验证记录的 EXE：逐项确认源码、版本、依赖及打包配置未变，EXE 与已验证产物 SHA256 相同，并复跑源码/EXE 冒烟。不以 checkout 后的文件时间戳代替内容核验；任何构建输入变化均须重新干净构建。

### 6. 提交和发布

只有前述检查全部通过后才执行：

1. 安全同步到本地 `main`：先 fetch 并核对远端，能快进时使用快进合入；不能快进或有未处理的用户改动时停止，不强制覆盖。
2. 把通过验证的 EXE 复制到根目录 `PaimonAssistant.exe`，核对 SHA256、文件大小和源码版本。仅暂存本次相关文件，检查 staged diff、敏感信息与 EXE blob。
3. 在 `main` 创建发布提交 `release: Paimon Assistant vX.Y.Z`，正文记录功能、验证结果、EXE SHA256。确认提交中实际包含 EXE，而非只存在于忽略的 `dist/`。
4. 创建注释标签 `vX.Y.Z`，指向同一个发布提交；标签说明包含功能、验证和 EXE SHA256。已有标签按前述幂等/冲突规则处理，不移动已发布标签。
5. 再次 fetch 核对远端，使用非强制、显式 ref 推送 `main` 和本版本标签；优先 `git push --atomic origin main refs/tags/vX.Y.Z`。若失败，先读取远端实际状态再重试，不假定任何 ref 已更新。
6. 核验远端 `main` 和标签解引用提交与本地发布提交一致；从 `main` 和标签固定链接实际下载 EXE，核对完整文件大小与 SHA256。只验证 HTTP 200 或网页存在不算完成。
7. 交付确认成功后，逐个删除已集成、已核查的远端临时分支，移除本次已完成 worktree，再清理相应本地分支。合入提交优先安全删除；补丁等价但提交不同的分支，仅在原提交已保存到本地 Git bundle 后删除。保留用户备份、有效环境和未知文件。
8. 再次 fetch/prune，并确认远端和本地 Branches 均只剩 `main`、历史标签完整、当前工作区在 `main`。有无法安全清理的独有工作时列明阻塞，不用破坏性清理强行满足数量。
9. 只有用户明确要求 GitHub Release 时，才基于已有版本标签创建发布说明或附件；无论是否创建 Release，`main`、Tags 和仓库内 EXE 都必须已交付。
